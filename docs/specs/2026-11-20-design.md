# Diseño: Análisis de tráfico aéreo y condiciones ambientales (Cómputo paralelo y distribuido, 2ª evaluación)

Fecha: 2026-11-20 (revisado: se quita Docker, todo corre en local en Mac)

## Intención y por qué

Proyecto de la 2ª evaluación de Cómputo paralelo y distribuido. El PDF del maestro pide un pipeline que lea APIs en la nube de forma concurrente, distribuya el procesamiento con MPI4Py, acelere cálculos numéricos con CUDA/CuPy/Numba, limpie y analice con Pandas y lo muestre en un dashboard. La pregunta de fondo es si el clima y la calidad del aire se relacionan con los retrasos y la actividad aérea.

## Metas

- Ingesta concurrente con `asyncio` + `aiohttp` desde AirLabs, OpenWeather, OpenAQ y ThingSpeak.
- Caché local de todo lo descargado para no gastar los límites de las APIs gratuitas.
- Distribución del procesamiento con MPI4Py (reparto por aeropuerto/región, agregación en rank 0).
- Cálculo numérico acelerado con backend intercambiable (`BACKEND` en `.env`):
  - `numba` (por defecto): Numba en CPU con `prange`, aprovecha todos los núcleos del M1 / M1 Pro.
  - `mlx` (opcional): GPU del chip Apple vía Metal, si el paquete está instalado.
  - `cupy`: CuPy / Numba CUDA, solo en el notebook de Colab (T4).
  - `numpy`: respaldo que siempre funciona.
- Limpieza y unificación con Pandas.
- Dashboard en Streamlit con las preguntas de análisis del PDF.
- Todo corre en local en Mac (M1 / M1 Pro, arm64) con un entorno virtual y un script de arranque.
- Las claves se pegan en un archivo `.env`; sin claves corre un modo demo con datos simulados.

## No metas

- Sin Docker.
- No hay GPU NVIDIA local; CUDA/CuPy se demuestra solo en Colab.
- No es un sistema de producción: sin autenticación, sin despliegue en la nube.
- No se usa Matplotlib como visualización principal (queda solo si se necesita para el reporte).

## Anti-metas

- Que solo funcione con claves reales: sin claves debe poder demostrarse igual.
- Que falle en Mac por depender de CUDA.
- Que un backend opcional que no esté instalado (MLX, CuPy) rompa el programa: debe caer automáticamente a `numba` o `numpy` con un aviso.

## Restricciones

- Equipos: Macs con chip M1 / M1 Pro (arm64), sin GPU NVIDIA.
- Planes gratuitos de las APIs con límite de consultas.
- MPI4Py en Mac requiere OpenMPI instalado con Homebrew (`brew install open-mpi`); va en el README. Si no está instalado, el procesamiento cae a `multiprocessing` con un aviso.
- Desde el entorno donde se escribe el código no hay red ni se pueden instalar paquetes: aquí se prueba la lógica con datos simulados y con los respaldos (numpy, multiprocessing); las corridas reales con claves, MPI, Numba y MLX las hace el equipo en sus Macs.

## Enfoques considerados

Almacenamiento:
- SQLite (elegido): un solo archivo, sin servidor, Pandas lo lee directo, alcanza para este volumen.
- MongoDB: encaja con JSON pero agrega un servicio que levantar en cada equipo.
- JSON/Parquet: simple, pero incómodo para consultar por rango de tiempo y aeropuerto.

Cálculo numérico:
- Backend intercambiable (elegido): Numba CPU por defecto, MLX opcional para la GPU del chip Apple, CuPy en Colab.
- Solo CPU: más simple, pero se pierde la parte de GPU que pide el PDF.

Ejecución:
- Local con entorno virtual (elegido, por decisión del equipo): aprovecha el chip del Mac directamente.
- Docker Compose: descartado por el equipo.

## Estructura propuesta

```
proyecto-trafico-aereo/
  .env.example              # AIRLABS_API_KEY, OPENWEATHER_API_KEY, OPENAQ_API_KEY, THINGSPEAK_*, BACKEND, DEMO_MODE
  requirements.txt
  setup.sh                  # crea el entorno virtual e instala dependencias
  run_pipeline.sh           # ingesta + mpirun + arranque de Streamlit
  src/
    config.py               # lectura de .env, aeropuertos/regiones por defecto
    ingest/                 # clientes async por API + modo demo
    storage.py              # SQLite con caché por consulta (fecha, endpoint, parámetros)
    clean.py                # Pandas: limpieza, unificación de estructuras, enriquecimiento
    compute/                # backend.py (numba/mlx/cupy/numpy), kernels: promedios, atípicos, correlaciones
    mpi_run.py              # reparto con mpi4py, agregación en rank 0
    app.py                  # dashboard Streamlit
  notebooks/colab_gpu.ipynb # demo CuPy/Numba CUDA y comparación de tiempos
  tests/
  README.md
```

## Decisiones de cómo (mis llamadas, corrígelas si no te parecen)

- SQLite en modo WAL; solo rank 0 escribe en la base. Los demás ranks reciben datos por MPI y devuelven resultados.
- Aeropuertos por defecto, configurables: CUU, MEX, GDL, MTY, TIJ. Región por defecto: México.
- ThingSpeak: se usa un canal público configurable por ID. Si el equipo tiene sensores propios, solo cambian el ID y la clave de lectura.
- Análisis del dashboard (del PDF): vuelos activos por región, rutas y aerolíneas más frecuentes, retrasos por aeropuerto, velocidad y altitud promedio, atípicos, actividad por hora del día, relación clima-retrasos y tráfico-condiciones ambientales.
- Modo demo: genera datos sintéticos con la misma forma que las respuestas reales para poder probar todo sin claves.
- Se incluye una comparación de tiempos entre backends (numpy vs numba vs mlx; cupy en Colab) para mostrar la aceleración.
- Los endpoints y campos exactos de cada API se verifican contra su documentación al implementar.
